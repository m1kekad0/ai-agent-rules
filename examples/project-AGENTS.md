# Project instructions — example

この例をプロジェクトに合わせて具体化する。vendor を採用する場合は公開再配布条件と必要な通知を先に確認し、実作業前に
`vendor/ai-agent-rules/AGENTS.md` と `vendor/ai-agent-rules/PROVENANCE.md` の固定コピーを読む。
pin が無い・壊れている場合はその利用を止め、実装担当が調整担当に報告する。
公開条件が未確定なら vendor やこの例をそのままコピーせず、目的・範囲・受入条件・許可操作・検証・独立レビュー・Human merge を定めた独立の最小 `AGENTS.md` で開始できる。
既存ゲート・環境指示・許可境界は引き続き適用する。

## Scope / acceptance

- 目的: 依頼された最小の機能と、その必要な検証を完成させる。
- 変更範囲: このプロジェクト内のみ。他の checkout や他者の差分は変更しない。
- 受入条件: 要求された振る舞い、プロジェクトのテスト・lint・build、別担当による独立レビュー1回。
- プロジェクト固有のコマンド・データ制約・追加の必須チェックをここに列挙する。

## Allowed operations / delivery

- この例だけでは権限を付与しない。依頼で許可されたローカル編集・検証・コミットを具体的に記載する。
- リモート作成・push・Draft PR・deploy・設定変更・費用発生の許可は別途依頼の範囲で確認する。
- 実装担当は不足する権限・判断を調整担当に報告し、調整担当が必要な場合だけ Human に相談する。
- リモート許可後は Draft PR と非同期レビューを使い、merge は Human が行う。
- 引き継ぎ: 変更ファイル、成果物、実際のチェック結果・未実行項目、HEAD、レビュー状態、制約、次の推奨操作。

## 公開プロジェクト向け補足 — 任意

- 新規公開プロジェクトは fresh な Git 履歴で始め、旧 Git 履歴、私有ログ、実データを一括移植しない。
- GitHub に表示された本人の noreply アドレスを repo-local に指定し、author / committer の有効値と実際の commit を確認する。global 設定を無断変更しない。
- 公開する出力は repo 相対パスにする。個人名を含まない作業パスは混入予防であり、ファイルアクセスの権限境界を変えない。
- 公開用 build 出力の確認と停止条件は[共通ルール](../AGENTS.md)に従い、許可するファイル集合と専用出力先をプロジェクトで具体化する。
- UI の変更前後の証拠は、公開確認済みの代表例と受入項目の索引を基本とし、必要な異常状態も含める。大量の画像取得・承認を必須にしない。
- 画像は元ファイルと PR 上の描画を実際に見て、読みやすさ、内容・メタデータの公開適否を確認する。公開後は認証なしの閲覧・取得も確認し、撮影元 SHA、fixture、viewport と確認した状態を示す。画像だけで操作成功や未検証のブラウザまで保証しない。アプリ UI に変更がない文書変更では画像を必須にしない。
